# Releases / Udgivelser

## English

`.github/workflows/release.yml` builds macOS, Windows and Android from the
same commit. A push of a `v*` tag creates a **draft** GitHub Release only after
all builds, configured signing operations and artifact checks succeed.
The workflow never makes a release public automatically.

1. Set the same version in `package.json`, `package-lock.json`,
   `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock` and `src-tauri/tauri.conf.json`.
   Follow [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md), including the pinned,
   authenticated node sidecar checks. Keep development features out of releases.
2. Run the checks below, commit the changes, and push the release commit.
3. Create a tag matching the app version, for example `v0.0.1`, on that commit
   and push that tag. A mismatched tag fails before building.
4. Wait for all jobs in **Release / Udgivelse**. Download `release-bundle` from
   the workflow run or inspect the draft's assets. Verify `SHA256SUMS` after
   extracting the downloaded artifact: `sha256sum --check SHA256SUMS`
   (`shasum -a 256 --check SHA256SUMS` on macOS).
5. Review signing labels, platform installation, release notes and the release
   checklist before manually publishing the draft. Unsigned artifacts need
   additional trust/installation steps; an unsigned APK cannot be installed
   until it is signed. A draft is not an updater feed accessible to users.

For a rehearsal, choose **Actions → Release / Udgivelse → Run workflow** and
leave `dry-run` enabled (the default). Branch runs are allowed for dry-run;
they use the checked-in version. All builds, configured signing and checksum
checks still run, and `release-bundle` is retained for seven days. No GitHub
Release is created. To create a draft with a manual run, select the matching
version tag and disable `dry-run`; a branch cannot publish.

Artifacts use `BitSov-<version>-<platform>-<signing-status>` names:

| Platform | Files | Signing label |
| --- | --- | --- |
| macOS universal (Apple Silicon and Intel) | `.app.zip` containing `BitSov.app`, `.dmg` | `signed-notarized` or `unsigned` |
| Windows x86_64 | NSIS `-setup.exe` | `signed` or `unsigned` |
| Android arm64 | release `.apk` | `signed` or `unsigned` |
| Desktop updater, when configured | macOS `.app.tar.gz`, payload `.sig` files, `latest.json`, `latest.json.sig` | Independent of OS signing |
| Every release bundle | `SHA256SUMS` covering every other asset | SHA-256 integrity checks |

The universal sidecar is assembled from separately authenticated arm64 and
Intel release binaries. Before bundling, both slices are compared with those
verified inputs again. No node binary is built from source by this workflow.
Existing build/package smoke workflows do not create GitHub Releases.

### Secrets

Configure these exact repository or organization secret names when signing
is required. This change adds no secrets. Never put values in source, workflow
inputs, logs or release assets. Build jobs have `contents: read`; only the
publish job has `contents: write`, and it receives no signing secrets.

| Exact secret name | Purpose |
| --- | --- |
| `APPLE_CERTIFICATE` | Base64-encoded Developer ID Application `.p12`, including its private key |
| `APPLE_CERTIFICATE_PASSWORD` | Password for that `.p12` |
| `APPLE_ID` | Apple account email for notarization |
| `APPLE_TEAM_ID` | Apple Developer team ID |
| `APPLE_APP_PASSWORD` | Apple app-specific password; mapped to Tauri's `APPLE_PASSWORD` environment variable |
| `WINDOWS_SIGNING_CERTIFICATE` | Base64-encoded code-signing `.pfx`, including its private key |
| `WINDOWS_SIGNING_PASSWORD` | Password for that `.pfx` |
| `ANDROID_KEYSTORE_BASE64` | Base64-encoded release keystore (`.jks` or compatible keystore) |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | Release key alias |
| `ANDROID_KEY_PASSWORD` | Password for the release key |
| `TAURI_SIGNING_PRIVATE_KEY` | Contents of a Tauri updater private key generated by `tauri signer generate` |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Optional updater key password; omit for an unencrypted key |

macOS signs and notarizes only when **all five** Apple secrets are nonempty.
Otherwise it clears the Apple signing environment, passes `--no-sign`, and
labels both artifacts `unsigned`. Tauri imports the certificate using
`APPLE_CERTIFICATE` / `APPLE_CERTIFICATE_PASSWORD`, discovers its identity,
and notarizes using `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_PASSWORD`.
The workflow verifies the app signature and stapled ticket, then submits,
staples and verifies the signed DMG's ticket too. See
[Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/).

Windows signs only with both Windows secrets. It imports the PFX into a
temporary runner's certificate store and supplies Tauri's
`certificateThumbprint`, `digestAlgorithm`, `timestampUrl` and `tsp` bundle
settings. Authenticode verification must pass for the executable and installer;
the imported key and temporary PFX are removed afterwards. See
[Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/).

Android builds an unsigned release APK through the checked-in Gradle project,
aligns it, and signs/verifies it with Android SDK `apksigner` only when all four
Android secrets are present. Passwords reach `apksigner` through environment
references. Credentials never enter Gradle configuration or caches, and the
temporary keystore is removed on exit. A partial Windows or Android secret
group fails the job; an entirely absent group produces `unsigned` artifacts.

Updater signing is separate from OS signing. If `TAURI_SIGNING_PRIVATE_KEY`
exists, the workflow uses Tauri's documented `TAURI_SIGNING_PRIVATE_KEY` and
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` environment variables with `tauri signer
sign --app-version`. It signs the final macOS archive and Windows installer,
then embeds their signatures and tag-specific download URLs in `latest.json`.
Both macOS architecture entries use the same universal archive. The manifest
also receives a detached signature. Tauri verifies the payload signatures;
`latest.json.sig` is an additional signature for independent manifest checks.
Without the private key, no updater archive, signature or manifest is emitted.
Shipping an in-app updater additionally requires configuring its matching
public key and endpoint; this workflow does not enable an updater in the app.
See [Tauri updater signing and manifest format](https://v2.tauri.app/plugin/updater/).

No configured signing, notarization or verification failure is ignored or
retried as unsigned. Any such failure blocks assembly and draft creation.
An existing release for the tag is never overwritten. If an upload fails,
inspect/delete the incomplete draft before starting a new run for that same
tag. Never replace a published tag or release to work around a failure.

### Local checks

Run Python 3.11+ and `actionlint` on the release workflow. The offline sidecar
checks also require GnuPG. These commands do not launch the app:

```sh
npm ci && npm test
python3 scripts/ci/test-release.py
python3 scripts/ci/test-release-macos-sidecars.py
actionlint .github/workflows/release.yml
bash -n scripts/ci/release-macos-sidecars.sh
npm run build
cargo test --manifest-path src-tauri/Cargo.toml --locked --lib
cargo test --manifest-path src-tauri/Cargo.toml --locked --test '*contract'
```

## Dansk

`.github/workflows/release.yml` bygger macOS, Windows og Android fra samme
commit. Et push af et `v*`-tag opretter kun en **kladde** til en GitHub-udgivelse,
når alle builds, konfigurerede signeringer og filkontroller er gennemført.
Workflowet offentliggør aldrig automatisk en udgivelse.

1. Brug samme version i `package.json`, `package-lock.json`,
   `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock` og `src-tauri/tauri.conf.json`.
   Følg [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md), herunder kontrollen af de
   fastlåste og autentificerede nodebinærer. Udelad udviklingsfeatures.
2. Kør kontrollerne ovenfor, commit ændringerne, og push udgivelsens commit.
3. Opret og push et tag, der matcher appversionen, eksempelvis `v0.0.1`.
   Et forkert tag afvises, før builds starter.
4. Afvent alle jobs i **Release / Udgivelse**. Hent `release-bundle` fra kørslen,
   eller gennemgå kladdens filer. Pak workflowarkivet ud, og verificér
   `SHA256SUMS` med kommandoen ovenfor.
5. Gennemgå signeringsstatus, installation på hver platform, udgivelsesnoter
   og tjeklisten, før kladden offentliggøres manuelt. Usignerede filer kræver
   yderligere tillids-/installationstrin; en usigneret APK skal signeres før
   installation. En kladde er ikke en offentligt tilgængelig opdateringskilde.

En prøvekørsel startes under **Actions → Release / Udgivelse → Run workflow**.
Lad `dry-run` være slået til (standard). En branch må bruges til prøvekørsel;
den anvender versionen i kildekoden. Alle builds, konfigurerede signeringer og
kontrolsummer udføres, og `release-bundle` gemmes i syv dage. Der oprettes ingen
GitHub-udgivelse. Vælg det matchende versionstag og slå `dry-run` fra for at
oprette en kladde manuelt. En branch kan ikke udgive.

Filnavne begynder med `BitSov-<version>-<platform>-<signeringsstatus>`:
macOS til Apple Silicon og Intel leveres som `.app.zip` og `.dmg` med mærket
`signed-notarized` eller `unsigned`; Windows x86_64 som NSIS `-setup.exe` og
Android arm64 som release-`.apk` med mærket `signed` eller `unsigned`.
`SHA256SUMS` dækker alle øvrige udgivelsesfiler. Den universelle nodebinær
samles af to autentificerede binærer, og begge arkitekturer kontrolleres igen
før pakning. Workflowet bygger ikke noden fra kildekode. Eksisterende
build-/pakkekontroller opretter ikke GitHub-udgivelser.

### Secrets på dansk

Brug de præcise navne nedenfor som repository- eller organisationssecrets.
Denne ændring tilføjer ingen secrets. Læg aldrig værdier i kildekode,
workflowinput, logs eller udgivelsesfiler. Buildjobs har `contents: read`;
kun publiceringsjobbet har `contents: write`, og det modtager ingen
signeringssecrets.

| Præcist navn | Formål |
| --- | --- |
| `APPLE_CERTIFICATE` | Base64-kodet Developer ID Application-`.p12` med privat nøgle |
| `APPLE_CERTIFICATE_PASSWORD` | Adgangskode til `.p12` |
| `APPLE_ID` | Apple-kontoens e-mail til notarbekræftelse |
| `APPLE_TEAM_ID` | Apple Developer-team-id |
| `APPLE_APP_PASSWORD` | Appspecifik Apple-adgangskode; overføres til Tauri som `APPLE_PASSWORD` |
| `WINDOWS_SIGNING_CERTIFICATE` | Base64-kodet signerings-`.pfx` med privat nøgle |
| `WINDOWS_SIGNING_PASSWORD` | Adgangskode til `.pfx` |
| `ANDROID_KEYSTORE_BASE64` | Base64-kodet release-keystore (`.jks` eller kompatibelt format) |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore-adgangskode |
| `ANDROID_KEY_ALIAS` | Alias for udgivelsens nøgle |
| `ANDROID_KEY_PASSWORD` | Adgangskode til nøglen |
| `TAURI_SIGNING_PRIVATE_KEY` | Indholdet af en privat opdateringsnøgle fra `tauri signer generate` |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Valgfri adgangskode til opdateringsnøglen; udelades for en ukrypteret nøgle |

macOS signeres og notarbekræftes kun, når **alle fem** Apple-secrets er udfyldt.
Ellers ryddes signeringsmiljøet, `--no-sign` anvendes, og filerne mærkes
`unsigned`. Tauri importerer certifikatet via `APPLE_CERTIFICATE` og
`APPLE_CERTIFICATE_PASSWORD`, finder identiteten og bruger `APPLE_ID`,
`APPLE_TEAM_ID` samt `APPLE_PASSWORD` til notarbekræftelse. Appens signatur og
vedhæftede billet kontrolleres. Den signerede DMG indsendes også, får sin egen
billet vedhæftet og verificeres. Se Tauri-linket til macOS ovenfor.

Windows kræver begge Windows-secrets. PFX importeres midlertidigt, og Tauri
konfigureres med `certificateThumbprint`, `digestAlgorithm`, `timestampUrl`
og `tsp`. Authenticode-kontrollen skal bestås for både app og installation.
Den importerede nøgle og den midlertidige PFX slettes bagefter. Se
Tauri-linket til Windows ovenfor.

Android bygger en usigneret release-APK med projektets Gradle-opsætning og
justerer filen med `zipalign`. SDK-værktøjet `apksigner` signerer og verificerer
kun, når alle fire Android-secrets findes. Adgangskoder overføres som
miljøreferencer, aldrig via Gradle eller caches. Keystore slettes ved afslutning.
En delvis Windows- eller Android-opsætning stopper jobbet. En helt tom gruppe
giver filer mærket `unsigned`.

Opdateringssignering er uafhængig af platformsignering. Når
`TAURI_SIGNING_PRIVATE_KEY` findes, bruger `tauri signer sign --app-version`
miljøvariablerne `TAURI_SIGNING_PRIVATE_KEY` og
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` til at signere det færdige macOS-arkiv og
Windows-installationen. `latest.json` indeholder deres signaturer og
downloadadresser for tagget; begge macOS-arkitekturer bruger samme universelle
arkiv. Manifestet får også en separat signatur. Tauri verificerer filernes
signaturer; `latest.json.sig` kan bruges til en særskilt manifestkontrol.
Uden den private nøgle oprettes ingen opdateringsarkiver, signaturer eller
manifester. En opdateringsfunktion i appen kræver desuden den matchende
offentlige nøgle og en opdateringsadresse. Workflowet aktiverer ikke funktionen
i appen. Se Tauri-linket til opdateringer ovenfor.

Fejl i konfigureret signering, notarbekræftelse eller verifikation ignoreres
aldrig og udløser ikke et usigneret alternativ. De blokerer samling og
oprettelse af kladden. En eksisterende udgivelse overskrives aldrig. Hvis
upload fejler, gennemgå/slet den ufuldstændige kladde før en ny kørsel for samme
tag. Udskift ikke et offentliggjort tag eller en offentliggjort udgivelse.
De lokale kontrolkommandoer ovenfor kræver Python 3.11+, `actionlint` og GnuPG
til sidecartestene; de starter ikke appen.
